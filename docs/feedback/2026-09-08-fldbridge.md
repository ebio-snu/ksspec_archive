## 1. 이 문서가 청구하는 것

`fldbridge` 는 **같은 `SPEC.md` 를 읽은 두 번째 독립 구현**이다. `ksdevice` 를 의존성으로
쓰지 않고 코드를 옮겨 오지도 않았다 — `SPEC.md` 와 `.spec` · `codes.json` ·
`protocols.json` 만 보고 `.spec` 파서를 새로 썼다. 대조가 성립하려면 그래야 했다.

**한 구현만 있으면 형식의 모호함이 드러나지 않는다.** 구현이 고른 값이 곧 형식의 뜻이
되기 때문이다. 두 번째 구현이 같은 문장을 다르게 읽으면 그때 문장이 보인다.

현재 `specs/defaults/*.spec` **17 개 전부에서 두 구현의 정규화 덤프 차이는 0** 이다.
아래는 **거기 이르는 과정에서 문서가 답을 주지 않아 걸린 자리**를 모은 것이다.

> **청구하는 것은 「형식이 틀렸다」가 아니라 「규약을 적지 않았다」이다.**
> 아래 항목 중 상당수는 규격 파일도 펌웨어도 참조 구현도 맞았고, 문서만 그 규약을
> 적지 않았다. 우리 결함이었던 것은 우리 결함이라고 적었다 (§4.1).

### 4.1 §5 · §5.4 — wire PDU 주소 규약이 문서에 없다 【갈림】

**§5 의 표는 `starting-register` 를 「**1-based** Modbus 주소」라고만 적는다.**
그 값이 wire 의 PDU 주소와 같은지(`N`), 일반 모드버스 관례대로 하나 빼야 하는지(`N-1`)를
말하지 않는다.

일반 모드버스는 데이터 모델 주소 `N` → PDU `N-1` 이다. **이 계보는 `N` 을 그대로 쓴다.**
그 규약이 형식 문서가 아니라 참조 구현의 주석에만 있다.

```python
# KS B 7958: Register N == PDU N (1-based wire).
# 도메인 1-based 주소를 wire PDU 로 그대로 전달.
```
출처: `ksdevice/src/ksdevice/client/adapters/pm3.py` — `read_holding_registers`

#### 두 구현이 실제로 갈렸다

| | `ksdevice` (파이썬) | `fldbridge` (Rust, 초판) |
|---|---|---|
| `starting-register` 203 을 wire 로 | PDU **203** | PDU **202** |

**우리가 틀렸다.** 형식 문서만 읽고 일반 모드버스 관례를 적용해 `addr - 1` 을 했다.
규격 파일도 펌웨어도 `ksdevice` 도 맞았다.

#### 실장비가 무엇을 냈나

한 칸 밀려 읽어도 모드버스는 정상 응답하고 형식도 맞는다. 오류를 내는 층이 없다.

```json
{"ct":{"sen-1":[null,1],"sen-2":[0.0,0], … "sen-30":[0.0,0]}}
```

실제 센서는 19.6 ℃ · 56 % 를 재고 있었는데 **그 값이 어디에도 없고 `0.0` 이 상태
0(정상)을 달고 올라갔다.** 고친 뒤 같은 규격 · 같은 장비에서:

```json
{"ct":{"sen-1":[19.478477,0], "sen-4":[57.57766,0], …}}
```

가짜 레지스터 은행과 로컬 TCP 서버로는 드러나지 않았다 — **보내는 쪽과 받는 쪽이 같은
오해를 하면 왕복 시험이 통과한다.** 우리 왕복 시험은 틀린 규약을 성실히 검증하고 있었다.

#### 재현

```bash
# 원시 수준 — 우리 변환을 거치지 않고 PDU 주소를 그대로 읽는다
python3 - <<'PY'
from pymodbus.client import ModbusSerialClient
c = ModbusSerialClient(port="/dev/ttyUSB0", baudrate=9600)
c.connect()
print(c.read_holding_registers(203, count=2).registers)   # float 19.03
print(c.read_holding_registers(212, count=2).registers)   # float 58.75
PY
```

`0_0_1_0_10_30.spec` 의 슬롯 1(`air-temperature-sensor`)은 `starting-register: 203`,
슬롯 4(`relative-humidity-sensor`)는 `212` 다. **값이 PDU 203 · 212 에 그대로 있다** —
뺀 자리가 아니다. 위 `ct` 의 `sen-1` · `sen-4` 와 슬롯 번호가 맞는다.

#### 왜 이것을 되먹이나

> 형식 문서가 규약을 적지 않으면 **독립 구현은 관례대로 짐작한다.** 실제로 그렇게 됐다.

우리 결함이지만, 두 번째 구현이 같은 자리에서 같은 짐작을 할 것이다. 그리고 그 짐작은
**숫자가 나오기 때문에** 시험을 통과한다.

#### 권장 문안 — §5 의 `starting-register` 행 또는 §5.4 에 한 줄

> `starting-register` 는 wire 의 PDU 주소와 같다 (`Register N == PDU N`).
> 일반 모드버스의 1-based 데이터 모델 주소 ↔ PDU 주소 관례(`N` → `N-1`)를 적용하지 아니한다.

### 4.2 §3 · §10.2 — 필수/선택 구분과 형식 밖 최상위 키의 처분이 없다 【갈림】

§3 의 필드 표에 **필수/선택 열이 없다.** 그래서 두 가지가 갈렸다.

| | `fldbridge` (Rust) | `ksdevice` (파이썬) |
|---|---|---|
| `_comment` 같은 **형식 밖 최상위 키** | 진단으로 **기록했다** | **넘겼다** |
| 최상위 **`CommSpec` 부재** | **넘겼다** | 진단으로 **기록했다** |

두 구현이 정반대로 갈렸다. 어느 쪽도 문서를 어기지 않았다 — 문서가 말하지 않기 때문이다.

#### 데이터에 실제로 있다

```bash
cd specs/defaults
grep -l '_comment' *.spec devices/*.spec
#   0_0_4_0_30.spec
#   0_0_2_9_10_4.spec

for f in *.spec; do python3 -c "
import json; d=json.load(open('$f'))
print('CommSpec 없음:', '$f') if 'CommSpec' not in d else None"; done
#   0_0_4_0_30_4.spec
#   0_0_4_0_30.spec
```

- `_comment` 는 **2 개 파일이 실제로 쓰고 있으나 §3 의 최상위 키 표에 없다.**
  `deny_unknown_fields` 로 짠 파서는 번들 규격을 거부한다.
  §8 · §11.1 · §11.2 · §11.3 의 예시 코드블록은 `jsonc` 로 표시돼 있으나, 실제 21 개
  파일은 전부 strict JSON 이고 주석 대신 이 키를 쓴다.
- 최상위 `CommSpec` 부재는 **§3 의 표가 이미 허용한다** — 「자체 영역이 없는
  노드(protocol 30 게이트웨이)는 적지 않는다 (§10.2)」. 그런데 그것이 §3 표의 **비고**
  문장이지 필수/선택 열이 아니라, 「부재를 진단으로 올려야 하는가」의 답이 되지 못했다.

#### 우리가 한 것

형식 밖 키는 **기록하고 넘어간다**(주소 산술과 무관하므로), `CommSpec` 부재는 §10.2 가
허용하는 상태로 보아 **오류로 적지 않는다** — 양쪽을 맞췄다. 맞춘 것은 대조를 위해서지
문서에 근거가 있어서가 아니다.

#### 권장 문안

- §3 · §4 의 필드 표에 **필수/선택 열**을 넣는다.
- §3 에 한 줄: *"`_` 로 시작하는 최상위 키는 주석이며 파서는 무시한다. 그 밖의 미정의
  키를 만났을 때의 처분(거부 / 무시 / 경고)은 〈여기서 정한다〉."*

### 4.3 §9.1.1 · §9.1.3 — 장비 코드 `0` 이 두 뜻을 겸한다 【갈림】\*

§9.1.2 에 따르면 `reserved` 는 **장비 코드 0 으로 해석돼 파서가 인스턴스를 만들지
않는다.** §9.1.3 의 `unknown-type` 행은 그 성질을 이렇게 적는다.

> `unknown-type` | warning | 알 수 없는 `Type` — **코드 0 이라 슬롯 검사가 꺼지므로** 타입당 1회 경고
>
> — `SPEC.md` §9.1.3

즉 **이름이 풀리지 않은 장비도 코드 0 이 된다.** 「빈 슬롯」과 「해석 실패」가 같은 값을
쓰고, 그 값은 슬롯 대조를 끄는 값이다.

**→ 구현의 사전 누락이 조용한 데이터 손실로 바뀐다. 그리고 검사는 통과한다.**

#### 실제로 그 형태로 나타났다

대조 1 회차에서 두 구현의 덤프가 **176 건 갈렸고**, 뿌리는 `relative-humidity-sensor`
슬롯 **3 개가 조용히 사라진 것**이었다. 그 이름이 코드 0 으로 풀렸고, 코드 0 은 슬롯
대조를 끄는 값이라 **틀린 값이 검사를 통과했다.**

\* **판정은 「`ksdevice` 결함」이었고 0.7.5 에서 고쳐졌다** (현재 17 / 17 · 차이 0).
그 결함 자체는 이 저장소로 청구할 것이 아니다. **형식 문서에 남는 것은 그 결함이
조용했던 이유** — 두 뜻이 한 값을 쓰기 때문에 검사층이 침묵했다는 것이다.

#### 재현

```bash
python3 tools/compare.py --specs <아카이브>/specs/defaults   # ksdevice 0.7.4 이하에서 176 건
```

#### 권장 문안

「빈 슬롯」과 「해석 실패」를 가르는 값을 두거나, **해석 실패를 경고가 아니라 오류로
규정한다.** 후자가 간단하다 — §9.1.3 의 `unknown-type` 을 `warning` 에서 `error` 로
올리고, 「코드 0 으로 강등하지 아니한다」를 명시한다.

### 4.4 §5 — 「첫 키만 의미를 가진다」가 JSON 객체 키 순서에 의존한다 【고름】

> `CommSpec` 의 키는 적용 표준 라벨이다. **첫 키만 의미를 가지며**, 둘 이상 정의해도
> 파서는 첫 항목을 사용한다.
>
> — `SPEC.md` §5

JSON 객체의 멤버 순서는 RFC 8259 가 의미를 두지 않는 자리다. **언어의 기본 자료형이 답을
바꾼다.**

```
① IndexMap (serde_json + preserve_order) 첫 키 = "KS X 3267"   ← 파일에 적힌 순서
② BTreeMap (serde_json 기본)             첫 키 = "KS B 7958"   ← 사전순
```

파이썬 `dict` 는 삽입 순서를 지키므로 ① 이 되고, **Rust 의 기본 구성은 ② 가 된다.**
같은 JSON 에서 「첫 키」가 갈린다.

#### 지금은 갈리지 않는다 — 그러나 형식이 허용한다

`CommSpec` **210 개 중 라벨이 둘 이상인 것은 0 개**라 잠복 상태다. 그런데 §5.5 는
*「한 파일 안에 라벨이 섞이는 것은 정상이다」* 라고 규정한다 — **형식이 허용하는
입력**이다.

#### 재현

```bash
python3 - <<'PY'
import json, collections
s = '{"CommSpec": {"KS X 3267": {}, "KS B 7958": {}}}'
print(next(iter(json.loads(s)["CommSpec"])))                     # KS X 3267
print(next(iter(sorted(json.loads(s)["CommSpec"]))))             # KS B 7958
PY
```

#### 우리가 한 것

`serde_json` 의 `preserve_order` 를 켜고 `IndexMap` 으로 받았다. **이 결정이 저장소 전체에
영향을 준다** — 상위 계층의 JSON 발행 순서까지 바뀐다. 형식 문서의 한 문장 때문에
구현이 전역 구성을 바꿔야 했다.

#### 권장 문안 (셋 중 하나)

1. §5 에 *"**파일에 적힌 순서의** 첫 키"* 라고 못박는다 — 가장 작은 변경이나 순서 의존이
   남는다.
2. **라벨이 둘 이상이면 오류**로 규정한다.
3. **protocol 코드로 고른다** (`protocols.json` 이 이미 코드 ↔ 라벨을 정한다) — 순서
   의존이 사라진다.

곁들여: §5.5 의 두 문장이 나란히 있어 오독을 부른다.

> 파서는 라벨 문자열을 대조하지 않고 **첫 키만** 집는다. … **라벨이 다르면 `items`
> 배치도 그 표준을 따른다.**

파서 관점에서 모순은 아니다(순서는 파일에 이미 적혀 있다). 그러나 「파서가 라벨을 보고
순서를 바꿔야 한다」로 읽힌다. *"라벨은 작성자를 위한 것이고 파서는 적힌 순서를 그대로
쓴다"* 를 명시하면 해소된다.

### 4.5 §8.2 — 폴백 문구가 두 가지로 읽힌다 【고름】

> 일치하는 opcode 가 없으면 (예: `OFF=0` 같은 공통 명령), 가장 짧은 opcode items 의
> 공통 prefix (`[operation, opid]`) 만 유효하다.
>
> — `SPEC.md` §8.2

| 읽기 | 뜻 |
|---|---|
| ⓐ | **모든** opcode items 의 공통 prefix 를 **계산**한다 |
| ⓑ | 가장 **짧은** opcode 의 items 를 **전부** 쓴다 |

한 문장에 「가장 짧은」과 「공통 prefix」가 함께 있어 둘 다 읽힌다.

#### 우리가 한 것 — ⓐ

공통 prefix 의 레지스터는 어느 opcode 에서든 같은 뜻이므로, **어느 명령이 올지 모르는
상태에서 유효하다고 말할 수 있는 것은 그것뿐**이다. ⓑ 는 가장 짧은 opcode 가 특수한
항목을 갖고 있으면 그것까지 유효하다고 말하게 된다. 괄호 안의 예시 `[operation, opid]`
도 ⓐ 와 맞는다.

#### 갈리는 데이터가 없다

번들 데이터에서는 두 읽기가 같은 답을 낸다. 게다가 `devices/actuator.spec` 코드 301
(`fnd`)은 `opcode: 0` 을 **명시**해 폴백을 아예 안 타게 해 두었다 — **예시로 든 바로 그
경우를 데이터가 회피하고 있다.**

#### 권장 문안

> 일치하는 opcode 가 없으면 **모든 `opcode` 항목의 `items` 공통 prefix** 만 유효하다.

곁들여 §8 은 *"flat `write.items` 와 공존한다 (둘 중 하나 사용)"* 라고만 적는다.
**동시에 적힌 파일을 만나면 무엇이 이기는지**, **둘 다 없으면 어떻게 되는지**가 없다
(데이터에서는 274 region 중 동시 0 건 · 둘 다 없음 0 건이라 잠복 상태다).

---

### 4.6 §9.2 — 자율배치 노드에 `write` 가 없으면 장비 write base 가 미규정 【고름】

§9.2 절차 4 는 이렇게만 말한다.

> 4. **노드 자체 영역 끝부터** 순차로 `starting-register` 계산
>
> — `SPEC.md` §9.2

**노드에 write 영역이 없고 장비 템플릿에 write 가 있으면 그 「끝」이 없다.**

`0_0_2_9_10_4.spec` 이 정확히 그 경우다 — protocol 10, `Devices: []`, **구동기 노드인데
`CommSpec.write` 가 없다.**

§10.2 는 *"자체 영역이 없으면 `Σ` 는 0 이고 자식은 `base` 부터"* 를 규정하지만 **그것은
`ConnectedNodes` 에 대한 규정**이고, `Devices` 에 일반화되는지가 없다.

#### 이것은 구현의 실제 blocker 다

protocol 10 기본 규격 5 개 중 **2 개가 자율배치**(`0_0_2_1_10.spec` ·
`0_0_2_9_10_4.spec`)다. 빼면 protocol 10 노드의 40 % 를 못 읽는다.

#### 재현

```bash
python3 -c "
import json; d=json.load(open('specs/defaults/0_0_2_9_10_4.spec'))
print(d['Type'], d['Devices'], list(d['CommSpec']['KS X 3267']))"
# actuator-node/auto  []  ['read']      ← write 가 없다
```

#### 우리가 한 것 — 죽인다

**501 로 치지 않았다.** 조용한 폴백을 두면 규격마다 다른 값이 굳고, 그 값이 틀렸을 때
아무도 모른다. 어느 조항 때문에 못 하는지 적고 죽는다.

#### 권장 문안

§9.2 에 한 줄. §5.1 의 표준 영역을 근거로 기본값을 규정하거나, 그런 조합을 금지한다고
명시한다.

> 노드에 해당 영역이 없으면 그 영역의 `Σ` 는 0 으로 보고, 첫 장비는 §5.1 의 표준 시작
> 주소(read 201 · write 501)부터 배치한다.

### 4.7 §8 — 평평한 배치에서 그 opcode 의 인자가 아닌 항목의 처분이 없다 【고름】

온실 구동기의 write 영역은 평평한 배치인 경우가 많다. 스위치 Lv1(장비 코드 102)이 그렇다.

```json
"write": {"items": ["operation", "opid", "hold-time"]}
```

그런데 `codes.json` 은 `201 ON` 에 **인자를 두지 않고**, `202 TIMED_ON` 에만
*"인자: 작동 시간 (time, hold-time)"* 을 붙인다. 즉 **`ON` 을 보낼 때 `hold-time`
레지스터에 무엇을 쓸지 정본이 없다.**

§8.2 는 opcode 별 배치(`operations`)가 **있을 때**의 활성 배치를 정하지만, **평평한
배치에서 opcode 마다 쓰이는 항목이 다른 경우**를 말하지 않는다.

#### 발행 표준 쪽은 답이 분명하다

`KS X 3267:2022` 는 명령마다 레지스터 내용을 따로 표로 둔다.

> **표 28 — 작동 시작 명령 스위치형 구동기 제어 정보**
> 제어명령 `operation` · 명령ID `opid` — 두 행뿐이다
>
> **표 30 — 지정 기간 작동 명령 스위치형 구동기 제어 정보**
> 제어명령 `operation` · 명령ID `opid` · **지속시간 `hold-time`** (uint16, 1 Word, M)

출처: `KS X 3267:2022` §6.3 「스위치형 구동기 제어」 표 28 · 표 30 (발행본 원문에서
확인). **`ON` 의 표에 `hold-time` 행이 없다 — 쓰지 않는 것이 표준의 뜻이다.**

#### 우리가 한 것

**값이 있는 앞부분만 쓴다.** `hold-time` 에 `0` 을 채우지 않는다 — 그 `0` 이 「즉시
정지」로 읽힐지 「무기한」으로 읽힐지 모르는 채로 값을 지어내는 것이 되기 때문이다.
다만 **건너뛴 뒤에 값이 남아 있으면 거절한다** — 중간을 비우고 뒤를 쓸 수는 없고,
억지로 이어 쓰면 값이 엉뚱한 레지스터로 간다.

```bash
cargo test --all-features opid_가_모드버스로_내려간다        # 201 ON → 506(hold-time) 비어 있다
cargo test --all-features 지속_시간이_붙으면_다른_opcode_다  # sec 가 붙으면 202 TIMED_ON
```

#### 권장 문안 — §8.2 에 한 줄

평평한 배치도 opcode 별 배치와 같은 규칙 아래 두면 된다.

> 평평한 배치에서 해당 opcode 의 인자에 해당하지 않는 항목은 기록하지 아니한다.
> 기록하지 않은 항목 뒤의 항목도 기록하지 아니한다.

### 4.8 §6.1 · §6.3 — `tz-offset` 이 시 단위라 분 단위 시간대를 담지 못한다 【표현력】

§6.1 의 표는 `tz-offset` 을 이렇게 정한다.

> `tz-offset` | 1 | int16 (signed) | 시간대 오프셋 (**시 단위**, 한국 `+9`) | P4 A.3 · P2 §6.3 표 8

모호하지 않다. **담지 못하는 값이 있을 뿐이다.**

| 담지 못하는 오프셋 | 지역 |
|---|---|
| `+05:30` | 인도 |
| `+09:30` | 호주 중부 |
| `+05:45` | 네팔 |

#### 왜 이것이 문제가 되나

이 항목이 **상위 표준의 시각 표현과 짝을 이룬다.** 노지 표준의 봉투 시각 `tm` 은
ISO 8601-1 이라 위 오프셋을 **표현할 수 있다.** 게이트웨이는 정확히 그 사이에 선다.

```
위(MQTT)  ISO 8601-1 문자열 + 오프셋   ← +05:30 표현 가능
아래(모드버스) epoch uint32 + tz-offset int16(시)  ← +05:30 표현 불가
```

즉 **시각 설정 명령이 그런 오프셋을 실어 오면 게이트웨이가 노드에 그대로 내려보낼 수
없다.** 우리 구현은 조용히 자르지 않고 오류로 되돌린다 — 자르면 30 분이 사라진다.

> 국내 운용에서는 나타나지 않는다 — 한국은 `+09:00` 고정이고 서머타임이 없다.
> 그러나 **표준 문안은 국내 한정을 말하지 않는다.**

#### 재현

```bash
cargo test --test spike_s9_time 분단위_시간대는_아래로_내려가지_않는다
```

#### 곁들여 — `epoch` uint32 의 범위

| 경계 | 값 |
|---|---|
| 상한 | `2106-02-07T06:28:15+00:00` (`u32::MAX`) |
| 하한 | 1970-01-01 이전 불가 |

관측 시각으로는 문제가 없다. **`epoch` 를 식별자 성분으로 쓰는 설계가 나오면 제약이
된다.**

#### 권장

`tz-offset` 의 단위를 **분**으로 바꾸면 int16 범위 안에서 전 세계 오프셋을 담는다
(`±1440` 이내). 다만 이것은 `SPEC.md` 가 인용하는 **KS B 7958-4 부속서 A.3 어휘**의
값이므로, 이 저장소가 단독으로 정할 것이 아니라 **그 표준 쪽과 함께 판단할 사안**으로
올린다. 어휘를 바꾸지 않기로 한다면, **분 단위 오프셋은 표현 불가임을 §6.1 의 비고에
명시**해 구현이 조용히 자르지 않게 하는 것이 차선이다.

## 5. 데이터 파일로 가는 항목

**여기 셋은 `SPEC.md` 의 문장이 아니라 `protocols.json` · `codes.json` 의 값 문제다.**
문서는 이미 그 파일들을 **「유일한 원천」**이라 선언했으므로(§5.5 · §7.1), 그 선언이
성립하려면 값이 채워져야 한다.

| # | 파일 | 무엇 | 갈래 |
|:---:|---|---|:---:|
| 5.1 | `protocols.json` | `device-label-exceptions` 의 코드 경계가 여덟 칸 늦다 | 값 정정 |
| 5.2 | `codes.json` | `device-type` 46 종이 protocol `10` 을 하나도 덮지 않는다 | 값 부재 |
| 5.3 | `codes.json` ↔ §7.1 | `range` 형태의 존재와 우선순위가 문서에 없다 | 문서 보완 |

---

### 5.1 `protocols.json` — `device-label-exceptions` 의 코드 경계

현재 값은 센서 코드 **25~34** 를 `KS B 7958` 라벨 예외로 잘라낸다.

```json
{"device-codes": ["25", …, "34"],
 "labels": ["KS B 7958"],
 "reason": "센서 코드 25~34 는 KS B 7958-5:2027 (rev6) 이 신설한 장비다 —
            2022 년 발행본인 KS X 3267 은 이들을 정의하지 않는다."}
```

**그 이유가 맞다면 경계가 틀렸다.** `KS X 3267:2022` 가 실제로 드러내는 센서 장치코드는
**1 ~ 18 뿐**이다.

#### 근거

- `KS X 3267:2022` 의 부속서 B(규격) 「코드 일람표」는 **제품 타입 · 상태 · 제어 명령 ·
  제어권** 네 표뿐이고 **장비 코드 표가 없다.** 장비 코드는 부속서 A(규격) 「디폴트
  레지스터 맵」의 `값(장치코드)` 열에 **예시 값으로만** 실린다.
- 부속서 A.1.2 가 드러내는 센서 장치코드는 **1 ~ 18**(레지스터 101~130, 131~200 은
  `reserved`). **코드 19 ~ 24 는 3267:2022 어디에도 없다.**
- 코드 목록의 취득은 다른 표준에 위임된다.

  > 노드 자동등록 기능을 지원하는 경우, … KS X 3286, **7.4** 의 디바이스 규격 취득
  > 과정에 따라 디바이스 규격을 확보하여 (…)
  >
  > — `KS X 3267:2022` §6.1.2

#### 재현

```bash
grep -n "장치코드" <표준원문>/KS-X-3267_2022.md
sed -n '2168,2212p;3447,3520p' <표준원문>/KS-X-3267_2022.md   # 부속서 A.1.2 · A.2.2
```

#### 권장

경계를 **18 과 19 사이**로 옮긴다 — 즉 `device-codes` 를 `19`~`34` 로 넓히거나,
`19`~`24` 를 별도 항목으로 두고 근거를 따로 적는다. 어느 쪽이든 **`reason` 문장과 값이
맞아야 한다.**

> ⚠️ 우리는 3267 쪽 경계만 확인했다. **코드 19 ~ 24 를 어느 표준이 신설했는지는 확인하지
> 못했다** 〔대조 필요〕 — `KS B 7958-5` rev6 인지 다른 판본인지에 따라 라벨이 갈린다.

### 5.2 `codes.json` — `device-type` 이 protocol `10` 을 하나도 덮지 않는다

`device-type` **46 종이 전부** `tier: "draft"` · `protocols: ["30","31"]` 이다.
protocol `10` 을 포함하는 항목은 **0 개**.

```bash
python3 -c "
import json; v=json.load(open('specs/codes.json'))['codes']['device-type']['values']
print(len(v), sum('10' in x.get('protocols',[]) for x in v))"
# 46 0
```

그런데,

- **§4.1** 은 device code 표의 원천을 `codes.json` 으로 지목하고,
- **§9.1.3** 은 `slot-code-mismatch` · `unknown-type` 검사를 `codes.json` 대조로
  규정하며,
- **protocol 10 규격 파일들은 그 이름들(`air-temperature-sensor` 등)을 그대로 쓴다.**

**→ protocol 10 노드의 devinfo 코드 ↔ `Type` 대조에 근거 데이터가 없다.**

비교하면 `product-type` 은 4 종 중 3 종이 `protocols` 에 `"10"` 을 포함한다 — **노드
타입만 덮여 있고 장비 타입은 비어 있다.**

#### 이것이 실제로 우회를 낳았다

3267 장비 코드 ↔ 노지 관측 코드 대응표를 만들 때 이 자리에서 막혀 **`KS X 3267:2022`
발행본 원문을 직접 열었다.** §7.1 이 *"수록되지 않은 코드를 만나면 소비처는 추측하거나
구현체에서 옮겨 오면 안 된다 — '아카이브에 근거가 없다'고 말할 것"* 이라고 규정하는데,
**그 말을 하고 나면 구현이 멈춘다.** 우회가 필요했다는 것 자체가 되먹임 근거다.

#### 권장

protocol 10 소관 장비 코드(§5.1 이 정리되면 **1 ~ 18** 과 구동기 `102` · `112`)에
`protocols` 에 `"10"` 을 더하고 `tier` 를 `normative` 로, `std` 를 `KS X 3267:2022` 로
적는다. 근거는 부속서 A 의 예시 값이므로 **`std` 에 「부속서 A 예시」임을 남기는 것이
정직하다** — 3267 에는 일람표가 없다.

### 5.3 `codes.json` 의 `range` 형태가 §7.1 에 없다

`codes.json` 에 구간 항목이 있다.

```json
{"range": [7, 99],    "name": "RESERVED",              "tier": "normative", "protocols": ["10"]}
{"range": [900, 999], "name": "VENDOR_SPECIFIC_ERROR", "tier": "draft",     "protocols": ["10","30","31"]}
```

§7.1 은 *"코드 값 ↔ 의미 대응"* 이라고만 하고 **구간 항목의 존재를 말하지 않는다.**
단일 코드와 구간이 겹칠 때 어느 쪽이 이기는지도 없다.

```bash
python3 -c "
import json; c=json.load(open('specs/codes.json'))['codes']
for k,v in c.items():
    r=[x for x in v.get('values',[]) if 'range' in x]
    print(k, len(v.get('values',[])), 'ranges:', len(r))"
# status 24 ranges: 2   (나머지 갈래는 0)
```

**우리가 한 것** — 단일 코드가 구간보다 구체적이므로 먼저 이기게 했다. 문서에 근거는
없다.

**권장** — §7.1 에 구간 형태와 겹칠 때의 우선순위를 적는다.

> 항목은 단일 `code` 또는 구간 `range: [시작, 끝]` 로 적는다. 같은 값을 단일 코드와
> 구간이 함께 덮으면 **단일 코드가 우선한다.**

## 6. 대조하지 못한 것

**시험 데이터가 아카이브에 없어 독립 구현이 대조할 입력을 갖지 못한 자리**다. 되먹임
항목으로 세지 않았으나, 두 번째 구현이 여기서 멈춘다는 사실은 남긴다.

| 절 | 무엇 | 상태 |
|---|---|---|
| §9.1.2 | `Type: "reserved"` 예약 슬롯 | 구현했으나 **아카이브에 `"reserved"` 문자열 0 건**. §9.1.3 이 참조 예로 드는 `999_999_2_1_10_24.spec` 은 `ksdevice` 패키지 번들이고 이 저장소에 없다 |
| §11.3 | 단일 장비 파일 | **그 형식의 데이터가 하나도 없어 구현하지 않았다** |

```bash
grep -rl '"reserved"' specs/                 # 0 건
ls specs/defaults/devices/                   # generic · protocol-specific 만
```

**권장** — 예약 슬롯을 가진 규격 하나와 단일 장비 파일 하나를 `specs/defaults/`
(또는 `SPEC_MANAGEMENT.md` §3 의 `tests/specs/`)에 두면 해결된다. 규정에 참조 예가
있는데 그 파일이 저장소 밖에 있으면, **참조 구현을 가진 쪽만 그 규칙을 시험할 수 있다.**
