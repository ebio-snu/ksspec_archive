# 장비 규격 관리 규칙

본 문서는 KS 스마트온실 장비 규격 저장소의 신뢰성, 추적성, 재현성을 위한 운영 규칙을 정의한다.
규격 파일의 문법과 의미는 [SPEC.md](SPEC.md)를 정본으로 하며, 본 문서는 그 파일의 작성·검토·배포 절차를 다룬다.

## 1. 관리 원칙

- `main` 브랜치는 **현재 배포 가능한 공식 규격**만 포함한다.
- 모든 공식 규격 변경은 변경 사유와 근거를 추적할 수 있어야 한다.
- 테스트를 위한 규격은 공식 규격과 파일 위치 및 상태를 분리한다. 테스트 데이터는 `main`에 포함될 수 있으나, 공식 패키지로 취급하거나 배포해서는 안 된다.
- 이미 배포한 규격은 삭제하거나 내용을 조용히 바꾸지 않는다. 오류 수정이나 대체가 필요하면 새 릴리스로 남기고 변경 이력을 기록한다.

## 2. 저장소와 브랜치 운영

| 구분 | 용도 | 포함 가능 내용 |
|---|---|---|
| `main` | 공식 배포 기준선 | 검토·검증을 통과한 `specs/defaults/` 규격과 문서 |
| `spec/<주제>` | 신규 규격 또는 규격 수정 | 작업 중인 공식 규격 변경 |
| `fix/<주제>` | 오류 정정 | 기존 규격의 명확한 오류 수정 |
| `docs/<주제>` | 문서 변경 | 형식 정의 및 관리 문서 변경 |
| `test/<주제>` | 테스트 코드·fixture 변경 | 테스트 데이터와 검증 도구 변경 |

브랜치는 가능한 한 짧게 유지하고, 작업 완료 후 Pull Request(PR)로 `main`에 병합한다. 장기적인 `test` 브랜치는 운영하지 않는다. 테스트용 규격의 보관·변경 이력은 브랜치가 아니라 아래의 테스트 데이터 영역에서 관리한다.

`main`은 보호 브랜치로 설정한다. 직접 push와 강제 push를 금지하고, 최소 1명의 검토 승인과 자동 검증 성공 후에만 병합한다.

## 3. 테스트 규격의 분리

테스트용 규격은 `specs/defaults/` 아래에 두지 않는다. 대신 `tests/specs/`에서
운영 규격과 같은 패키지 구조와 파일명 규칙을 적용한다.

```
tests/
└── specs/
    └── <패키지명>/  # 운영 패키지와 동일한 구조의 테스트용 규격 패키지
        ├── vendor.json
        ├── <org>_<mfg>_<type>_<code>_<protocol>_<max_devices>.spec
        └── devices/  # 필요 시 device 템플릿
```

- `tests/specs/`의 각 패키지는 `specs/defaults/` 및 외부 제조사 패키지에 적용되는 디렉터리 구조, 파일명, JSON 형식 규칙을 모두 따라야 한다.
- 테스트 규격에도 실제 제조사명·인증 코드·운영 모델명을 사용하지 않는다. 식별자와 모델명은 명백한 시험용 값으로 작성한다.
- 임시 조사 파일, 개인 장비 덤프, 민감 정보는 커밋하지 않는다. 공유가 필요한 경우에는 익명화한 fixture로 변환한다.
- 유효하지 않은 JSON 또는 형식 정의를 위반한 규격은 저장소에 등록하지 않는다. 오류 사례의 검증은 테스트 코드에서 직접 구성하거나 별도의 입력 방식으로 처리한다.
- 테스트 규격은 배포 패키지 목록, 카탈로그 생성, 릴리스 산출물에서 제외한다.

`tests/specs/`가 아직 없다면, 테스트 규격을 처음 추가하는 변경에서 위 구조를 함께 만든다.

## 4. 변경 요청(PR) 필수 정보

규격 파일을 추가·수정·폐기하는 PR에는 다음 내용을 포함한다.

1. 변경 대상 파일과 대상 장비 식별값: `(org, mfg, type, code, protocol, max_devices)`
2. 변경 유형: 추가, 오류 수정, 호환 확장, 호환성 영향 변경, 폐기 중 하나
3. 변경 사유와 근거: KS 표준의 조항·표 번호, 제조사 공식 자료, 시험 결과 등
4. 통신 영향: 변경된 레지스터 주소, `items`, 데이터 타입, 명령 또는 device code
5. 호환성 및 권장 버전 변경 수준(§5)
6. 검증 결과와, 필요한 경우 실제 장비 또는 시뮬레이터 시험 결과

PR 제목은 `spec:`, `fix:`, `test:`, `docs:` 중 하나로 시작한다. 예: `fix: 0_0_2_1_10의 hold-time 레지스터 크기 정정`.

## 5. 버전 및 릴리스

공식 배포본은 Git 태그 `vMAJOR.MINOR.PATCH`로 식별한다. 태그는 `main`의 병합 커밋에만 생성한다.

| 변경 수준 | 적용 기준 | 예시 |
|---|---|---|
| `PATCH` | 기존 소비자에게 의미·통신 호환인 오류 정정 또는 문서 정정 | 설명 오탈자, 누락된 이름 보완 |
| `MINOR` | 기존 규격을 깨지 않는 신규 장비·프로토콜·선택 기능 추가 | 새 `.spec` 파일 추가 |
| `MAJOR` | 기존 소비자의 해석·통신 결과를 바꿀 수 있는 변경 | 레지스터 주소·타입·의미 변경, 파일명 식별자 변경 |

`vendor.json`의 `version`은 해당 장비 패키지의 배포 버전이며, 기본 패키지의 공식 릴리스 태그와 함께 갱신한다. 외부 제조사 패키지는 자체 버전을 유지하되, 같은 호환성 판단 기준을 권장한다.

각 릴리스에는 다음을 포함한 변경 기록을 남긴다.

- 태그와 배포 일자
- 추가·수정·폐기된 규격 파일 목록
- 호환성 영향 및 업그레이드 방법
- 근거 문서 또는 이슈/PR 참조

## 6. 호환성 영향 변경과 폐기

이미 공개된 파일에서 레지스터 주소, `items` 순서, 데이터 타입, 명령 코드, 장비 식별값을 바꾸면 기존 컨트롤러에 영향을 줄 수 있다. 이런 변경은 원칙적으로 기존 파일을 덮어쓰지 말고 다음 순서를 따른다.

1. 기존 규격에 폐기 사유와 대체 규격을 변경 기록으로 남긴다.
2. 새 식별자 또는 새 프로토콜 버전에 대응하는 규격 파일을 추가한다.
3. 최소 한 번의 `MINOR` 릴리스 동안 이전 규격을 유지한다.
4. 제거가 불가피하면 `MAJOR` 릴리스에서 제거 사유와 마이그레이션 방법을 공지한다.

KS 표준의 정정·개정으로 기존 해석을 바로잡는 경우에도, 근거 조항과 영향을 받는 컨트롤러 동작을 PR과 릴리스 기록에 명시한다.

## 7. 검증 기준

`main`에 병합하기 전, 변경 범위에 맞춰 다음을 확인한다.

- 모든 `.spec` 및 `vendor.json`이 유효한 JSON이다.
- 파일명이 규격 내부의 장비 식별 정보 및 적용 프로토콜과 일치한다.
- 필수 필드, 허용 `Class`/`Type`, `CommSpec` 구조, item 이름과 데이터 크기가 [SPEC.md](SPEC.md)를 따른다.
- read/write 레지스터 주소가 규칙에 맞고 장비 간 영역이 겹치지 않는다.
- `Devices`, device 템플릿, gateway 자식 노드, fallback 규칙이 의도대로 해석된다.
- 테스트가 필요한 신규 규격은 `tests/specs/`에 동일한 구조와 파일명 규칙으로 추가한다.

자동 검증 도구가 아직 없는 항목은 PR 검토자가 수동 확인하고, 도구가 마련되는 즉시 CI 검증으로 전환한다.

## 8. 책임과 예외

- 규격 작성자는 변경 근거와 검증 결과를 제공한다.
- 검토자는 KS 표준 적합성, 주소·데이터 형식의 정확성, 기존 규격과의 호환성을 확인한다.
- 릴리스 담당자는 승인된 `main` 상태에만 태그를 만들고 변경 기록을 게시한다.

긴급 정정도 PR·검토·태그 원칙을 따른다. 이 규칙을 예외로 적용해야 한다면, 예외 사유·영향 범위·사후 검증 계획을 PR과 릴리스 기록에 남긴다.
